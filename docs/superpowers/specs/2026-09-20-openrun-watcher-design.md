# ctwatch — 캐치테이블 오픈런 감시기 설계

## 목적
watchlist에 (식당, 날짜들, 인원)을 적어두면, 그 날짜의 예약이 풀리는 시각 T를 계산해
로컬 맥에서 T 전후로만 감시하다가, 열리는 즉시 알림 + 날짜·인원이 맞춰진 예약 페이지를
평소 쓰는 브라우저에 띄운다. **시간 선택과 확정은 사람이 한다.**

## 하지 않는 것 (의도적)
- 로그인/쿠키 사용, 예약 생성(`create`) 자동화
- `time-slots` 호출 — `encryptedParamString` + `c1~c4` 자동화 방지 장치가 걸려 있음. 우회하지 않는다.
- 상시 폴링, 취소표 줍기, 문서화되지 않은 파라미터 추측

## 검증된 사실 (2026-09-20, 실제 응답 기준)
| 항목 | 내용 |
|---|---|
| 접근 | `ct-api.catchtable.co.kr`는 Cloudflare Bot Management. 일반 클라이언트 403, Chrome TLS 위장(`curl_cffi`) 200. **사용자 승인 범위: 비로그인 공개 GET 폴링에 한함.** 언제든 막힐 수 있음 |
| 식당/일정 | `GET /api/v4/shops/{alias}` → `shopDetailVO.shopRef`, `shopOpenScheduleList[]` |
| 일정 타입 | `scheduleType "B"`(월간)만 확인: `monthlyOpenDate`, `availableOpenTime "HHMM"`, `start/endMonthIndex`, `openStart/EndDate`. 상시 오픈 식당은 `[]` |
| 가용성 | `GET /api/reservation/v2/dining/calendar?shopRef=` → `days[].availability.{status, personCounts}` |
| 가용성 (대체) | **`calendar`가 가용성을 안 주는 식당이 있다** — 에스쿱(`esquep`)은 늘 `{"availabilityEnriched": false, "days": []}` (2026-09-22 실전 준비 중 발견). 웹앱은 모든 식당 페이지에서 `GET /api/reservation/v1/dining/day-slots?shopRef=&tableSeqs=&personCounts=`(14일치, `data[].{date, availableStatus, availablePersonCounts}`)를 부르고 여기엔 이런 식당의 가용성도 들어 있다. `client.calendar()`는 `availabilityEnriched`가 false면 day-slots로 받고, 그 식당은 이후 day-slots만 쓴다. 이런 식당의 조회 범위는 14일이라 그 밖 날짜는 규칙 2(서버가 준 마지막 날짜)로 정각 알림이 된다 |
| 오픈 전 상태 | 식당 단위 응답에서도 확인: 에스쿱 10/1~10/5가 `BEFORE_OPEN`, `availablePersonCounts: []` (9/25 00:00 오픈 예정분) |
| 상태값 | `AVAILABLE` / `BEFORE_OPEN` / `CLOSED` / `DAY_OFF` / `PHONE_INQUIRY` |
| 조회 범위 | **오늘부터 고정된 끝 날짜까지.** 9/20(일)엔 9/20→10/31(42일), 9/21(월)엔 9/21→10/31(41일) — 끝은 안 움직였다. 그 끝이 '그 주 일요일+41일'인지 '다음 달 말일'인지는 두 값이 같은 주에만 관측해 **미확정**. 범위를 옮기는 파라미터는 확인되지 않음 |
| 딥링크 | `app.catchtable.co.kr/ct/shop/{alias}?personCount=N&date=YYMMDD` — 열면 페이지가 그 날짜 시간대를 스스로 조회 |
| 성능 | calendar 응답 중앙값 31ms(keep-alive), 폴링 주기 337ms → 감지 지연 평균 0.2s / 최악 0.45s. rate limit burst 1200 |
| 병목 | **감지가 아니라 페이지 로드.** 딥링크 → 시간대 데이터 도착: 2.4s, 방금 열었던 상태면 0.86s (각 1회 실측, 비로그인 Chromium). 폴링 간격을 줄이는 건 틀린 레버 |

## 구조 (모듈 4 + CLI)
- `client` — 위 GET 2개. 응답 파싱만.
- `schedule` — `open_time_for(schedules, target_date) -> datetime | None` 순수 함수. **확인된 형태만** 계산: 타입 B이고 한 번에 한 달분만 여는 일정(`startMonthIndex == endMonthIndex`). 여러 달 일정, 그 달에 없는 오픈일(예: 9월 31일), 빠진 필드는 추측하지 않고 None → watchlist의 `open_at` 안내.
- `watchlist` — YAML 로드/검증. `open_at`은 시간대가 없을 때만 KST로 보고, 명시된 시간대는 변환한다.
- `watcher` — 한 식당의 한 오픈 시각을 T-60s ~ T+30s 감시. **감시 단위는 (오픈 시각, 식당)이고 단위마다 독립 스레드·독립 세션**이다: 느린 식당이나 시각이 가까운 다른 일정이 서로를 막지 않고, 오류 횟수도 식당별이다. 같은 식당·같은 시각의 target(인원수만 다른 경우 등)은 한 주기에 조회 1회를 공유한다(calendar 요청엔 인원이 없다). 동시에 나가 있는 요청은 세마포어로 4개까지.
- **정각 알림은 조회 루프가 아니라 별도 타이머**(`alarm_at`)가 맡는다 — 네트워크가 필요 없는 일이 조회 지연에 밀리면 안 된다. 실측(진짜 스레드·시계): 다른 식당의 모든 요청이 1.5s씩 멈추는 동안 정각 알림 T+0.01s, 정상 식당 감지 T+0.25s.
- `__main__` — `ctwatch check <yaml>` (계산 결과만 출력), `ctwatch run <yaml>` (대기+감시, `caffeinate`로 절전 방지).

## 감시 규칙
0. **T-60s 준비**: target마다 딥링크를 미리 열고(캐시 예열 + 사람이 로그인 상태 확인) calendar를 1회 조회해 본다. 실패하면 경고음과 함께 알린다 — 차단·네트워크 문제를 T-3s가 아니라 1분 전에 알기 위함. 이 실패는 규칙 4의 횟수에 넣지 않는다.
1. target 날짜가 calendar 응답 안에 있으면 **폴링 모드**: `AVAILABLE`이고 인원이 `personCounts`에 있으면 즉시 알림+딥링크.
2. **범위 밖 날짜는 정각 알림**(T에 알림+딥링크, 감지 신호 없음). 판정은 날짜별로, 두 단계:
   - 두 가설(일요일+41일 / 다음 달 말일) 중 먼 쪽보다도 뒤인 날짜는 **조회 전에, 시작하자마자** 타이머에 등록한다. 네트워크가 필요 없는 알림이 조회 결과(성공이든 연속 실패든)를 기다리면 서버가 느린 바로 그 순간에 늦는다 (수정 전 재현: T+4s → 수정 후 실측 T+0.01s, 조회 0건).
   - 애매한 날짜는 **서버가 실제로 준 마지막 날짜보다 뒤일 때만** 범위 밖으로 본다. 이 판정은 T-60s 사전 조회 응답에도 적용한다 — 그 응답을 버리면 정각 직전 조회가 연속 타임아웃일 때 알림 등록이 T+4s로 밀린다(수정 후 실측: T+0.00s, 조회 1건). 빈 응답이나 범위 안인데 빠진 날짜는 일시적 이상으로 보고 계속 조회한다.
   - 한 target에 범위 안·밖 날짜가 섞여 있으면 날짜별로 갈린다: 밖은 정각 알림, 안은 폴링. 둘 다 울리면 날짜가 다른 탭이 각각 열린다.
3. `BEFORE_OPEN`을 본 적 있는데 T 이후 전부 다른 상태면 "열리자마자 마감"으로 종료. **단, 그 target의 모든 날짜가 응답에 보일 때만** — 빠진 날짜가 곧 열릴 수 있는데 보이는 날짜만 보고 끝내면 안 된다.
4. **그 식당의** 조회가 연속 5회 실패(차단 등)하면 조회를 포기하되 **정각 알림은 남긴다**(정각 전에 사람을 헛부르지 않는다. 이미 지났으면 즉시). T+30s 경과 시엔 시간 초과로 즉시 넘긴다. 폴링 요청 타임아웃은 1.5s (오픈 순간 서버가 가장 느린데, 멈춘 요청 하나에 5s씩 묶이면 안 된다. curl_cffi에서 `timeout=None`은 무제한이므로 값이 있을 때만 넘긴다).
5. **늦게 켠 경우**: T+30s 안이면 감시한다(식당 조회 중에 정각이 지나도 마찬가지). 이미 T-5s를 지났으면 준비 단계(규칙 0)는 건너뛴다 — 미리 열기가 감지 후 열기와 겹쳐 같은 탭이 두 번 뜬다.
6. **실패 격리**: 시작 시 식당 조회가 실패한 대상(일시 오류, alias 오타)은 알리고 건너뛰며 나머지는 진행한다. 감시 스레드가 예외로 죽으면 **먼저 실패를 기록하고**(대체 동작까지 실패해도 종료 코드에 남게) 그 대상들을 정각 알림으로 넘긴다. 이미 연 (target, 날짜)는 다시 열지 않되, 브라우저 실행 자체가 실패했으면 완료로 치지 않아 재시도가 가능하다. 시작 시 식당 조회는 순차이고 타임아웃 2s(평소 0.15s)다 — 병렬화·선착 시작은 하지 않았다: 영향이 '정각 몇 초 전에 켰는데 여러 식당이 동시에 멈춘' 경우로 좁다. 둘 중 하나라도 있으면 종료 코드가 0이 아니다.
7. **어떤 경로로 끝나든 딥링크는 연다** — 사람이 이어받을 수 있게.

## 실전 검증 (진행 중)
가까운 실제 오픈 이벤트 2건을 찾아 `launchd` 1회용 작업으로 예약했다(세션과 무관하게 돌고, 끝나면 스스로 삭제). `scripts/realtest.py`가 진짜 `ctwatch run`을 돌리면서 조회마다 대상 날짜 상태를 시각과 함께 `logs/realtest-<이름>.log`에 남긴다.
- 에스쿱: 2026-09-25 00:00 (day-slots 경로, 10/16은 범위 밖 → 정각 알림 경로)
- 스시대옥: 2026-09-25 12:00
- 볼 것: `BEFORE_OPEN → AVAILABLE` 전환이 T 대비 언제 일어나는가, 감지 → `open`까지 지연, 오픈 순간의 응답 지연·오류

## 미검증 가정 (코드에 주석으로 표시)
- 오픈 전 날짜가 calendar에서 `BEFORE_OPEN`으로 보인다 (검색 결과에서만 관측). 틀려도 규칙 3이 발동 안 할 뿐 규칙 1은 동작.

## 테스트
실제 캡처 응답을 픽스처로. `watcher`는 가짜 시계/클라이언트 주입으로 모든 종료 경로 검증. 마지막에 실제 API로 `check` 1회.
